# ИИ-стилист

ИИ-стилист — отдельный сложный механизм внутри более широкой системы [ИИ-контент-завода](ии-контент-завод.md). Контент-завод решает, какой контент сделать из результата; стилист решает, какие реальные товары каталога образуют сильные сочетания.

## Текущая роль

Базовый flow строится вокруг якорного товара:

```text
якорь
  ↓
несколько стилистических направлений
  ↓
механический shortlist по Visual Passport
  ↓
сравнение паспортов одним модельным запросом
  ↓
несколько сильных финалистов
  ↓
проверка реальных фото
  ↓
победитель
```

Главная текущая бизнес-задача — стабильно находить 1–2 сильных публикуемых образа в день, а не перебирать все возможные комбинации.

## Ключевой стратегический вывод: один якорь даёт несколько образов

Шаг сравнительного ranking по паспортам полезен не только тем, что выбирает победителя. В хорошем run он сразу показывает несколько валидных способов носить один и тот же якорный товар.

То есть ИИ-стилист надо понимать шире:

> это система исследования пространства сочетаний вокруг якорного товара, а не только бинарный checker «сочетается / не сочетается» и не только механизм выбора одного winner.

Один run потенциально содержит:

- лучший вариант для немедленной публикации;
- несколько альтернативных сильных сочетаний;
- объяснение, почему каждый вариант работает;
- отклонённые сочетания и конкретные причины;
- несколько разных стилистических направлений для одного товара.

Это важно, потому что те же результаты можно использовать не только в рубрике «образ дня», но и в рубрике «с чем носить». Подробнее — в [стратегии ИИ-контент-завода](ии-контент-завод.md).

## Что не надо терять после run

Сейчас модель тратит reasoning на большое количество пар. Стратегически эта информация ценна сама по себе и в будущем её стоит переиспользовать.

Потенциальная память стилиста:

- одобренные пары anchor + partner и их оценки;
- отклонённые пары и структурированные причины;
- сильные альтернативы, которые не стали финальным winner;
- ranking нескольких сочетаний вокруг одного anchor;
- полезный editorial angle / copy для сильной пары.

Это пока не приоритет реализации. Сначала надо доказать, что текущий pipeline стабильно даёт хорошие образы. После этого такая память может:

- снизить повторные расходы на LLM/VLM;
- не заставлять систему заново «открывать» уже проработанные сочетания;
- постепенно накопить собственную compatibility-базу;
- стать основой для рубрики «с чем носить» и библиотеки готовых сочетаний.

Кэш не должен быть вечной истиной. Пересмотр нужен, если изменились фото товара, Visual Passport, prompt/model, доступность или бизнес-контекст.

## Текущая механика разнообразия

Недавнее использование товара — механический business constraint, а не стилистический сигнал для модели.

Сейчас логика такая:

- последние 10 генераций — hard exclude;
- 11–49 генераций назад — partner снова разрешён, но получает линейный mechanical penalty;
- с 50-й генерации penalty = 0.

Этот penalty должен влиять на retrieval/shortlist, но не говорить ИИ, что вещи «хуже сочетаются».

## Improvements

### Soft recency для anchor

Сейчас после 10 hard runs anchor сразу возвращается в обычный random pool. В будущем лучше оставить случайность, но уменьшать вероятность выбора недавно использованного anchor в диапазоне 11–50 runs.

Идея:

- 0–10 — нельзя выбирать;
- 11–50 — можно, но вероятность ниже;
- 50+ — обычная вероятность.

### Weighted-random anchor selection

Вместо полностью равного random можно использовать weighted random, не превращая выбор в детерминированный top-1.

Возможные механические веса:

- давность последнего использования;
- editorial potential по Visual Passport: expression, activity, необычная geometry/details, выраженность archetype;
- качество и наличие `worn_full` / `worn_crop` фото;
- confidence/completeness Visual Passport;
- freshness — новые товары, которые ещё не получали контент;
- при необходимости commercial priority, brand/category coverage.

LLM на каждом run для расчёта веса не нужен. Лучше дешёвый, прозрачный deterministic score из уже имеющихся данных. Если editorial potential плохо описывается механически — его можно один раз предрассчитывать при обработке паспорта/медиа.

Цель — не «всегда выбирать самый сильный anchor», а немного повышать вероятность товаров, из которых легче получить сильный публикуемый контент, сохраняя широкую ротацию каталога.

## Приоритет

Пока не усложнять. Сначала валидировать реальными run'ами цепочку:

`directions → shortlist → passport ranking → image comparison → финальный образ`.

Weighted anchor selection и явный cache/memory layer внедрять тогда, когда логи покажут, что именно выбор anchor, повторы или повторный reasoning стали заметным bottleneck.
