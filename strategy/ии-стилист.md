# ИИ-стилист

ИИ-стилист — отдельный сложный механизм внутри более широкой системы [ИИ-контент-завода](ии-контент-завод.md). Контент-завод решает, какой контент сделать из результата; стилист решает, какие реальные товары каталога образуют сильные сочетания.

## Текущая роль

Базовый flow строится вокруг якорного товара:

```text
якорь
  ↓
несколько стилистических направлений
  ↓
механический shortlist по Visual Passport
  ↓
сравнение паспортов одним модельным запросом
  ↓
несколько сильных финалистов
  ↓
проверка реальных фото
  ↓
победитель
```

Главная текущая бизнес-задача — стабильно находить 1–2 сильных публикуемых образа в день, а не перебирать все возможные комбинации.

## Ключевой стратегический вывод: один якорь даёт несколько образов

Шаг сравнительного ranking по паспортам полезен не только тем, что выбирает победителя. В хорошем run он сразу показывает несколько валидных способов носить один и тот же якорный товар.

То есть ИИ-стилист надо понимать шире:

> это система исследования пространства сочетаний вокруг якорного товара, а не только бинарный checker «сочетается / не сочетается» и не только механизм выбора одного winner.

Один run потенциально содержит:

- лучший вариант для немедленной публикации;
- несколько альтернативных сильных сочетаний;
- объяснение, почему каждый вариант работает;
- отклонённые сочетания и конкретные причины;
- несколько разных стилистических направлений для одного товара.

Это важно, потому что те же результаты можно использовать не только в рубрике «образ дня», но и в рубрике «с чем носить». Подробнее — в [стратегии ИИ-контент-завода](ии-контент-завод.md).

## Что не надо терять после run

Сейчас модель тратит reasoning на большое количество пар. Стратегически эта информация ценна сама по себе и в будущем её стоит переиспользовать.

Потенциальная память стилиста:

- одобренные пары anchor + partner и их оценки;
- отклонённые пары и структурированные причины;
- сильные альтернативы, которые не стали финальным winner;
- ranking нескольких сочетаний вокруг одного anchor;
- полезный editorial angle / copy для сильной пары.

Это пока не приоритет реализации. Сначала надо доказать, что текущий pipeline стабильно даёт хорошие образы. После этого такая память может:

- снизить повторные расходы на LLM/VLM;
- не заставлять систему заново «открывать» уже проработанные сочетания;
- постепенно накопить собственную compatibility-базу;
- стать основой для рубрики «с чем носить» и библиотеки готовых сочетаний.

Кэш не должен быть вечной истиной. Пересмотр нужен, если изменились фото товара, Visual Passport, prompt/model, доступность или бизнес-контекст.

## Editorial Window как вход в ИИ-стилиста

Проблема текущего генератора не только в качестве отдельных образов. Несколько хороших образов подряд могут давать хаотичную ленту, если они относятся к разным persona, occasion, уровню sensuality и эстетике. Поэтому стилист должен уметь работать внутри текущей [Editorial Window](content-strategy.md#editorial-window).

### Editorial Window — отдельная сущность

Editorial Window должна стать first-class сущностью контент-завода, а не только текстом в prompt.

Минимально она описывает:

- название / тему;
- цель контента;
- primary persona и optional secondary personas;
- mood;
- occasion;
- season;
- formality;
- sensuality;
- palette;
- style / silhouettes;
- visual language;
- период или статус активности.

На первом этапе window можно создавать вручную. Автоматическая генерация Editorial Window с нуля — low priority.

Content/образ должен знать, к какой window он относится. Для воспроизводимости генерации полезно хранить не только `editorial_window_id`, но и snapshot ключевых параметров window в run/content generation: последующее редактирование window не должно переписывать смысл уже сгенерированного результата.

### Подбор продуктового пула под window

Отдельная операция контент-завода: по Visual Passport собрать товары, которые подходят текущей Editorial Window.

Пример:

```text
Editorial Window
  ↓
criteria from persona / mood / occasion / palette / formality / sensuality
  ↓
Visual Passport filtering / scoring
  ↓
eligible product pool
  ↓
manual review if needed
  ↓
collection for outfit generation
```

Пул не обязан быть абсолютно однородным. Его задача — убрать очевидно чужие текущей главе товары и оставить стилисту достаточно пространства для сильных сочетаний.

Практически это можно материализовать через уже существующую Collection и переиспользовать текущий collection-scoped generation, вместо создания отдельного параллельного механизма хранения product pool.

### Два способа связать window со стилистом

#### Вариант A — ограничить только продуктовый пул

Текущий flow стилиста не меняется. Перед запуском ему просто передаётся collection/product pool текущей Editorial Window.

```text
Editorial Window
  ↓
product pool
  ↓
current AI stylist flow unchanged
```

Плюсы:

- минимальное вмешательство в уже работающий flow;
- дешёвая и понятная механика;
- проще тестировать, что именно улучшило coherence;
- меньше риска переусложнить prompts.

Минус: стилист знает только допустимый набор товаров, но не знает, почему именно эта window существует и какой soft direction внутри неё предпочтителен.

#### Вариант B — передавать Editorial Window в reasoning стилиста

Window становится контекстом для модельных шагов. Например, модель знает, что сейчас нужен `City Professional`, `polished`, sensuality `2/5`, black/cream/chocolate, work → dinner.

Контекст может влиять на:

- выбор anchor;
- stylistic directions;
- passport ranking;
- image comparison;
- финальный выбор winner.

Плюс: стилист может различать два технически совместимых образа и выбирать тот, который лучше продолжает текущую editorial story.

Минусы:

- сильнее связывает стилиста с контент-стратегией;
- усложняет prompts и debugging;
- есть риск over-constrain: все образы внутри window начнут выглядеть одинаково.

### Предпочтительный путь: staged hybrid

Пока базовая гипотеза такая:

**Phase 1 — сначала ограничить пространство, не переписывая стилиста.**

1. Editorial Window как сущность.
2. Manual creation/editing.
3. Сбор подходящих товаров по Visual Passport.
4. Результат — обычная Collection/product pool.
5. Текущий AI stylist работает внутри этого пула почти без изменений.

Это самый дешёвый способ проверить, решает ли сама сегментация каталога проблему хаоса.

**Phase 2 — добавить window как soft context только там, где этого не хватает.**

Если внутри хорошего продуктового пула стилист всё ещё генерирует неподходящий tone, тогда передавать window в `directions`, ranking и/или финальный visual check. Не обязательно дублировать весь editorial context на каждом шаге.

Полезное разделение:

- **hard constraints**: допустимые product IDs / collection, availability, category/slot, техническая совместимость;
- **soft constraints**: persona, mood, sensuality, formality, style, occasion, palette preference.

Идея: Editorial Window должна сужать пространство решений и задавать направление, но не превращаться в жёсткий шаблон, где каждый пост обязан иметь одинаковый цвет, силуэт и настроение.

## Текущая механика разнообразия

Недавнее использование товара — механический business constraint, а не стилистический сигнал для модели.

Сейчас логика такая:

- последние 10 генераций — hard exclude;
- 11–49 генераций назад — partner снова разрешён, но получает линейный mechanical penalty;
- с 50-й генерации penalty = 0.

Этот penalty должен влиять на retrieval/shortlist, но не говорить ИИ, что вещи «хуже сочетаются».

## Improvements

### Soft recency для anchor

Сейчас после 10 hard runs anchor сразу возвращается в обычный random pool. В будущем лучше оставить случайность, но уменьшать вероятность выбора недавно использованного anchor в диапазоне 11–50 runs.

Идея:

- 0–10 — нельзя выбирать;
- 11–50 — можно, но вероятность ниже;
- 50+ — обычная вероятность.

### Weighted-random anchor selection

Вместо полностью равного random можно использовать weighted random, не превращая выбор в детерминированный top-1.

Возможные механические веса:

- давность последнего использования;
- editorial potential по Visual Passport: expression, activity, необычная geometry/details, выраженность archetype;
- качество и наличие `worn_full` / `worn_crop` фото;
- confidence/completeness Visual Passport;
- freshness — новые товары, которые ещё не получали контент;
- при необходимости commercial priority, brand/category coverage.

LLM на каждом run для расчёта веса не нужен. Лучше дешёвый, прозрачный deterministic score из уже имеющихся данных. Если editorial potential плохо описывается механически — его можно один раз предрассчитывать при обработке паспорта/медиа.

Цель — не «всегда выбирать самый сильный anchor», а немного повышать вероятность товаров, из которых легче получить сильный публикуемый контент, сохраняя широкую ротацию каталога.

## Приоритет

Пока не усложнять. Сначала валидировать реальными run'ами цепочку:

`directions → shortlist → passport ranking → image comparison → финальный образ`.

Следующий крупный слой поверх этого flow — Editorial Window. Его MVP лучше начать с first-class entity + product pool/Collection, не переписывая reasoning стилиста сразу.

Weighted anchor selection, явный cache/memory layer и глубокую window-aware prompt orchestration внедрять тогда, когда реальные логи покажут соответствующий bottleneck.
